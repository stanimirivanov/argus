# ADR-0003: Use JSON Schema and generated contract bindings

- Status: Accepted
- Date: 2026-09-16
- Milestone: M02 - Contracts and identity
- Deciders: Argus maintainers
- Supersedes: None
- Superseded by: None

## TL;DR

- Use JSON Schema Draft 2020-12 as the canonical wire-contract language.
- Publish strict, versioned contract majors in a semantic-versioned bundle.
- Generate and check in Go and Python models with pinned, reproducible tools.
- Make one manifest-owned fixture corpus the compatibility authority for every
  language.
- Validate structural rules before decoding and enforce cross-field invariants
  in small hand-written consumer boundaries.
- Reuse Perfeng's proven contract-management pattern, not its product-specific
  schemas or implementation repository.

## Context

Argus needs stable identities and evidence metadata before catalog persistence,
change impact, test selection, or adaptation can exchange trustworthy values.
Go is the control-plane language, while later analysis may use Python and
framework adapters may use TypeScript. Making one language's internal structs
the source of truth would couple those components to implementation details and
make compatibility accidental.

The contract representation must be readable in pull requests, usable without
a schema registry or network connection, strict enough to reject producer
mistakes, and capable of generating ordinary language models. Compatibility
must be tested against real documents, including failures that a structural
schema cannot express.

Perfeng already applies language-neutral contracts, generated bindings, and
compatibility fixtures successfully. Its performance-execution vocabulary and
release lifecycle remain independent under ADR-0001 and ADR-0002. The useful
reuse boundary now is the engineering pattern. Extracting a library before
Argus has a second proven consumer would add cross-repository release coupling
without eliminating meaningful implementation.

## Decision

### Canonical representation and ownership

Argus contracts use JSON Schema Draft 2020-12. Schemas, fixtures, generation,
and compatibility checks live in the Argus repository and require no network
at validation time after dependencies are resolved. Schemas use stable HTTPS
identifiers but validation MUST use local resources and MUST NOT fetch those
identifiers.

Objects are strict by default and reject unknown fields. Requiredness,
nullability, formats, numeric bounds, enumerations, and identifier syntax are
declared explicitly. Human descriptions clarify meaning but do not substitute
for executable constraints.

The root `contracts/manifest.json` is the inventory authority. It declares the
bundle version, schema, generated outputs, fixtures, and the expected structural
and binding validity of every fixture. Validation fails for undeclared or
duplicate schemas and fixtures.

### Versioning

The contract bundle follows semantic versioning. Each contract has a separate
integer wire major in its name and directory, such as `kernel/v1`. A breaking
wire change creates a new major beside the old one and increments the bundle
major. Backward-compatible capability additions increment the bundle minor;
non-wire corrections increment its patch.

Documents carry their contract/schema version, bundle version, and minimum
reader bundle version. Producers MUST NOT emit a representation that their
declared readers cannot accept. A major migration preserves the preceding
schema and fixtures until its supported consumers have moved.

### Generated bindings and validated boundaries

Go bindings are generated by the version pinned in the root Go module. Python
Pydantic v2 bindings are generated by the versions locked with uv. Both outputs
are checked in so consumers, code review, and builds do not depend on generation
at runtime.

One repository command generates both languages into a temporary directory.
Its normal check mode compares generated bytes with the committed outputs; its
explicit write mode replaces them. Generated outputs MUST be deterministic and
MUST NOT contain timestamps, host paths, or ambient-environment values.

Generated types are not by themselves a trusted boundary. Go validates a raw
document against the complete schema before unmarshalling it. Python validates
through generated strict Pydantic models. Small hand-written wrappers in both
languages enforce relationships such as repository, suite, revision, expiry,
and bundle consistency. Consumers MUST use these wrappers or an equivalent
boundary proven by the common corpus.

### Compatibility corpus

Every contract includes representative positive and negative fixtures. The
manifest distinguishes schema validity from complete binding validity so a
fixture may be structurally valid but fail a cross-field invariant. Go and
Python tests read the same manifest and document bytes; language-specific
fixture lists are prohibited.

Compatibility checks are part of `make validate` on Ubuntu and Windows.
Regeneration, schema checks, language type checks, and compatibility tests are
separate failures so a contributor can identify the violated boundary.

### Scope and Perfeng boundary

M02 defines only the shared identity, provenance, confidence, time, validation,
and compatibility kernel. Feature-specific messages are introduced with their
first executable consumer. This avoids freezing speculative selection,
adaptation, or performance contracts.

Argus does not depend directly on the `perfeng-contracts` repository and does
not copy Perfeng's performance schemas. Both projects may align conventions.
A common library or independently released shared contract artifact requires
the multi-consumer evidence and extraction decision specified in ADR-0001.
The actual Argus–Perfeng integration contract remains M09 work.

## Alternatives considered

### Protocol Buffers as the canonical representation

- Benefits: Mature multi-language generation, compact binary messages, and
  strong field-number evolution conventions.
- Costs and risks: Adds a compiler/toolchain and binary inspection burden;
  JSON-facing GitHub, CI, and configuration boundaries still need translation;
  local format constraints and human-authored examples are less direct.
- Reason not selected: The first contracts are evidence documents exchanged at
  repository and API boundaries where readable JSON and offline schema
  validation are more valuable than transport efficiency.

### Hand-written models in each language

- Benefits: Idiomatic language types and no generator dependencies.
- Costs and risks: Requiredness, enum, strictness, and format behavior drift;
  every change needs synchronized implementation and review in each language.
- Reason not selected: Parallel models make compatibility a convention rather
  than an executable, language-neutral boundary.

### Make Go types canonical and derive other schemas

- Benefits: One control-plane implementation and excellent Go ergonomics.
- Costs and risks: Wire semantics become constrained by Go representation;
  other languages depend conceptually on an internal package; JSON Schema
  details that Go cannot express naturally require generator annotations.
- Reason not selected: The contract belongs to all producers and consumers,
  not to the current control-plane implementation.

### Reuse or extract `perfeng-contracts` immediately

- Benefits: One contract toolchain and fewer superficially duplicated files.
- Costs and risks: Couples independent products, releases, reviews, and
  vocabulary before common semantics are proven; encourages generic abstractions
  around different authority boundaries.
- Reason not selected: Reusing the proven pattern captures the benefit now.
  Artifact or library extraction remains available when two consumers prove it.

## Consequences

### Positive

- Go and Python exchange the same documented values without importing one
  another's implementation types.
- Strict schemas and negative fixtures catch misspellings, unsupported versions,
  invalid ranges, and semantic reference mismatches early.
- Checked-in bindings are reviewable while reproducibility prevents hidden
  manual edits or generator drift.
- Offline compatibility tests are deterministic and suitable for every CI lane.
- The pattern extends to TypeScript or another language without changing the
  canonical representation.

### Negative

- The repository now carries Go and Python toolchains for one delivered slice.
- Generated code increases the diff and must be regenerated on schema changes.
- JSON Schema cannot express every relationship; wrappers must remain aligned
  across languages through fixtures.
- Strict unknown-field rejection requires deliberate producer/readers rollout
  for additions.

### Neutral or follow-up

- The kernel is not a network API, schema registry, package publication system,
  catalog model, or persistence schema.
- M03 adds catalog-specific contracts only with ingestion and query behavior.
- TypeScript generation is added when an adapter consumes a contract; M02 does
  not add an unused third binding.
- Python dependencies are development and reference-consumer tooling in this
  repository; deployable ownership is decided with a real Python component.

## Compatibility and migration

This is the first Argus wire-contract release, so no existing consumer migration
is required. Future breaking changes create a parallel contract major. A
producer moves only after its consumers demonstrate support through the shared
corpus, and old fixtures remain until the compatibility window closes.

The generated package paths contain the contract major. Bundle versions live in
documents and the manifest rather than Git paths. Repository-local generated
packages are not a promise that external repositories may import Argus source;
external use requires a separately versioned artifact decision.

## Security and operations

Every incoming contract document is untrusted. Consumers validate size at the
transport boundary when one exists, then validate schema and semantic
invariants before domain use. Unknown fields, non-HTTPS repository locators,
mutable revision names, invalid timestamps, and unsupported versions fail
closed.

Schemas and fixtures contain no credentials or production data. Validation does
not dereference remote schema identifiers. Generators execute only through the
pinned repository command and are dependency-, vulnerability-, and license-
reviewed under the development policy. Generated files are inspected like
source and never executed merely because a document requested it.

## Validation

The decision is verified by:

- an offline Draft 2020-12 schema and manifest validator;
- positive and structural-negative fixtures;
- a structurally valid but semantically invalid fixture;
- Go and Python consumer tests over the identical manifest-owned corpus;
- strict unknown-field and format behavior;
- byte-for-byte regeneration checks for both bindings;
- Python lint and type checks plus the existing Go checks;
- `make validate` on Ubuntu 24.04 and Windows Server 2025; and
- no runtime or build dependency on a sibling Perfeng checkout.
